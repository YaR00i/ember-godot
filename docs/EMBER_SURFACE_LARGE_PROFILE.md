# Ember Surface — профиль большой dense-карты

Дата: 5 сентября 2026. Версия редактора: v2.47. Reference runtime: Godot
4.7.2, Windows; CPU-профиль запускается headless, визуальная проверка — Forward+.
Источник: read-only
`content/world_surfaces/agent_sandbox_surface.tres`; все временные save/reopen
файлы и JSON пишутся в `user://`.

## Данные и решение

Surface имеет 24×24 игровых блока, voxel-grid 384×32×384 и 4 718 592 dense
slots. Занято 557 205 (11.8%). `voxels`, `transparency` и три column channels
занимают 10 321 920 bytes (9.84 MiB) в несжатом рабочем представлении.

`ResourceLoader.CACHE_MODE_IGNORE` для текстового `.tres` стабильно занимает
около 0.80 с (после прогрева OS cache), save — 0.13 с,
reopen сохранённого файла — 0.81 с. Это заметная, но ограниченная стоимость;
она не доказывает необходимость второго storage owner, sparse serializer или
chunk persistence. Каноническая schema v4 остаётся dense.

## Измеренные пути

- Синхронный `Surface Canvas.open_surface`: 0.79 → 0.12 с.
- Полный heightfield: 0.61 → 0.045 с; reference и optimized arrays совпадают.
- Hide/isolate group view: 0.71 → 0.019 с; clear — около 0.018 с.
- Exact 16×32×16 chunk: 25.5 → 5.9–6.6 мс в среднем.
- Frame drain: 1–2 быстрых chunks за 6–11 мс; медленный fallback
  остаётся ограничен одним законченным chunk за итерацию.
- Полная Forward+ сборка 576 chunks завершилась за 6.05 с / 472 rendered frames
  без видимых швов или пропавших участков; disposable screenshot сохранён в
  `user://ember_large_surface_profile.png`.
- Connected selection до atomic cap: около 0.10 с pure work; UI выполняет её
  3 ms slices. Подготовка MultiMesh overlay для 32 768 voxels — около 0.044 с,
  обычно 10 slices. Здесь production-код не менялся.
- Преобразование 32 768 изменённых индексов в 144 затронутых chunks — около
  0.015 с. Оно выполняется один раз при commit, не на каждом pointer move.

## Обоснованные изменения

1. При occupancy ≤33% и palette index ≤32 heightfield перечисляет ненулевые
   palette entries через native `PackedByteArray.find`; dense/high-palette
   модели сохраняют прежний bounded column scan.
2. Editor-only visibility/isolation не меняет terrain, поэтому повторная
   пересборка использует уже вычисленный canonical heightfield. View filter не
   попадает в Resource или Undo.
3. Grid и region overlays читают тот же heightfield cache вместо повторного
   поиска верхнего voxel по Y.
4. Исторически (5 сентября) Voxel Tools строил exact terrain только для сухих
   chunks, а чанки с водой целиком переходили на SurfaceMesher. Этот пункт
   **устарел**: с 14 сентября native terrain компонуется с прежним water/foam
   overlay внутри общего adapter. Наличие воды теперь само по себе не означает
   fallback земли. Stock остаётся для draft, недоступного native и случая,
   когда native не вернул mesh; точная внутренняя причина последнего здесь не
   измерялась.
5. Preview queue имеет 6 ms soft budget: быстрые chunks группируются в один
   кадр, а один дорогой chunk всё равно завершается и затем управление
   возвращается editor loop.

## Editor Canvas: стоимость редактирования v1.5 (2026-09-24)

Это **отдельное диагностическое окно**, не основная 3D-вкладка Godot editor.
Сценарий вызывает методы Canvas для одного paint-мазка из 40 точек напрямую,
без мыши и pointer routing; между точками ждёт один `process_frame`. Источник
каждой попытки — новая глубокая копия одной Surface. Перед измерением путь
прогревается тем же мазком с Undo, проверяется полное восстановление `voxels`
и `transparency`; два повтора идут в чередующемся порядке. Для сухого участка
взята непрерывная строка `(256,14,32)→(295,14,32)` (171 изменённый voxel),
для водного — 40 точек одной строки `(55,4,247)→(97,3,247)` с тремя пропусками
между соседями (646 voxels). Внутри каждой пары Legacy/Adaptive исходник и
последовательность правок идентичны. Context OFF, Shadows ON, MSAA 4x.

Godot 4.7.2 Forward+ / RTX 5070, окно 1600×900; `Engine.max_fps=0`, project
max FPS=0, window/project VSync mode=1, частота монитора≈200 Hz. Плато около
200 FPS в прежнем render-sample соответствует VSync на этом мониторе; глобальные
настройки не менялись. Параметры запуска и viewport записаны в JSON.

После локальной правки, среднее двух прогретых повторов, миллисекунды:

| Участок / режим | Кисть | Данные | Поиск чанков | UI во время hold | Adapter во время hold | Hold wall¹ | Exact queue wall / adapter | Undo / Redo direct |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Сухой · Legacy 16 | 2,7 | 1,8 | 0,5 | 51,4 | 357,3 | 516,5 | 39,4 / 30,7 | 50,2 / 52,2 |
| Сухой · Adaptive 32 | 2,7 | 1,5 | 0,6 | 51,0 | 630,7 | 757,6 | 89,5 / 81,3 | 98,9 / 97,9 |
| У воды · Legacy 16 | 2,5 | 2,6 | 0,7 | 35,5 | 263,0 | 399,9 | 31,3 / 24,3 | 44,5 / 41,8 |
| У воды · Adaptive 32 | 2,4 | 2,6 | 0,7 | 36,5 | 759,0 | 869,6 | 59,7 / 55,4 | 76,7 / 75,3 |

¹ `hold_wall` включает 40 ожиданий кадров. Их wall-интервалы составляли в
среднем 456,6/698,0 мс (сухой Legacy/Adaptive) и 355,5/824,3 мс (у воды).
Они **включают** работу mesher в этих кадрах: складывать frame-await и adapter
нельзя. Очередь измеряется отдельно как latency «последний запрос чанка →
начало rebuild»: в среднем 4,0/3,0 мс на сухом участке и 1,9/1,2 мс у воды.
Её latency по параллельно ожидающим чанкам тоже нельзя суммировать. Таймеры
вложенных операций учитываются эксклюзивно.

Все 8 попыток использовали native exact path, stock/draft fallback не
наблюдался. Водный mesh surface присутствовал у каждого чанка водной линии;
это не fallback земли. Во время hold сухая линия вызывала в среднем 80/40
перестроек чанков (Legacy/Adaptive), водная — 43/40. Один чанк повторялся до
17/16 раз на сухом участке и до 19/31 раз у воды. При этом средний **полный
вызов adapter** на чанк стоил примерно 4,5/15,8 мс (сухо) и 6,1/19,0 мс
(вода). Это время включает неизвестную долю подготовки, native `build_mesh`
и композицию внутри adapter; чистое время native meshing **не измерено**.
Подготовка editor-side данных, назначение материалов и mesh instance занимали
единицы миллисекунд суммарно. Pointer-up UI/overlays — около 16–18 мс в обоих
режимах; обновление heightfield при Undo — около 0,5–1,2 мс. Доказательств
нового полного сканирования Surface при маленькой правке в editor-пути нет.

Единственная локальная лишняя работа: каждый не-материальный жест без нужды
нормализовал полный канал прозрачности. До исправления подготовка paint стоила
в среднем 54–58 мс (почти целиком эта нормализация), после — менее 0,1 мс.
Regression test проверяет отсутствие этой аллокации для обычного stroke и её
сохранение для material stroke. Повторный A/B подтвердил, что hold, exact и
Undo/Redo Adaptive заметно дороже и после правки: она не маскирует основную
причину. Укрупнение региона повышает стоимость повторного полного вызова
adapter, несмотря на меньшее число чанков. Изменение стратегии live preview
или частичного meshing требует отдельного архитектурного контракта; Phase 2
здесь не реализована.

Подробные per-chunk координаты, размер, draft/exact, наблюдаемый backend,

## Основная 3D-вкладка: большие мазки (следующий срез, ручной gate открыт)

В действующем `Редактировать мир` добавлена выключенная по умолчанию кнопка
`Начать запись мазков`. Она записывает в память путь ввода основной 3D-вкладки,
параметры/экранные точки кисти, реально изменённые voxels, отдельные интервалы
выбора точки, очереди ввода, UI/оверлея, вычисления кисти, записи черновика,
ожидание brush queue, dirty/rebuild каждого чанка и возраст **первого**
ещё не обслуженного изменения. Запись JSON происходит только после кнопки
`Остановить и сохранить запись`; абсолютный путь `user://ember_world_edit_trace_*.json`
показывается в статусе редактора. В JSON также есть `Engine.max_fps`, VSync,
renderer, аргументы запуска, queue-drained и первый `frame_post_draw` после
последнего назначения mesh. Последний показатель — лишь proxy передачи кадра
рендеру, не доказательство видимости конкретного пикселя. Медиана/p95/max
интервалов `frame_post_draw` относятся к редактору во время мазка; они не
эквивалентны FPS отдельного Canvas. Время полного вызова native adapter включает
его внутреннюю подготовку и композицию; чистое native meshing не измерено.
`-1` в полях возраста/кадров означает «не измерено» (например, очередь была
непустой до записи или headless не даёт rendered frames). Для реальной мыши
фиксируется момент входа события в editor callback, не аппаратный момент
поступления от устройства; у синтетической траектории отдельно есть плановое
время и опоздание обработчика.

Минимальная ручная проверка: открыть отдельную тестовую копию карты в Godot
Forward+, перейти в основную `3D`, включить `Редактировать мир`, прогреть сцену
до опустошения очереди. Нажать `Начать запись мазков`, выполнить один привычный
непрерывный paint, дождаться отображения, остановить запись. Повторить на той же
исходной копии для shape-инструмента (`Лепка · добавить` либо используемого
рельефного инструмента), затем для более длинного мазка через границы чанков и
нескольких мазков подряд. Перед стрессом около 50 тыс. изменений не сохранять
черновик как авторскую карту; проверять Undo/Redo и визуальный возврат, а при
сомнении закрыть тестовую сцену без сохранения. Реальная запись основной
3D-вкладки теперь получена; её исходные данные и ограничения приведены ниже.
Ручная оценка ощущения кисти **после** локальной оптимизации всё ещё открыта.
Headless не создаёт редакторский 3D-preview.

Вторичный headless fixture `tools/qa_world_edit_large_stroke.gd` подаёт события
через `EmberWorldEditor.forward_input` (не через Canvas), но его preview
редактора в headless не привязан к черновику. Он проверяет только input/brush/
data/history; цифры нельзя переносить на FPS, rebuild или задержку видимого
обновления основной вкладки. После прогрева и возврата к одинаковому массиву:

| Синтетический жест | Реально изменено voxels | Brush evaluation | Batch prepare + draft write | Undo / Redo |
|---|---:|---:|---:|---:|
| Paint, контрольный большой | 12 880 | ~88 мс | ~38 мс | <1 / <1 мс |
| Paint, обычный | 39 568 | ~248 мс | ~113 мс | ~1–2 / ~1–2 мс |
| Paint, стресс | 82 640 | ~648 мс | ~286 мс | ~3 / ~2 мс |
| Shape `add` | 39 568 | ~248 мс | ~119 мс | ~1 / ~1 мс |

Отдельный прогон с 90-мс заданной временной траекторией, без правила «одна
точка на кадр», изменил те же 39 568 voxels; максимальное опоздание передачи
события обработчику в этом headless fixture — около 6 мс. Это не замер
физического мышиного ввода. Два последовательных paint-мазка и полное
восстановление массива после двух Undo/Redo прошли. Времена ожидания jobs
не складываются с активными этапами как CPU-время. Тест
`tools/test_world_edit_trace.gd` проверяет first-dirty age и подключение
пассивного sink к общей projection. Этот headless fixture не служит замером
реального тормоза основной 3D-вкладки.

### Реальная очередь кисти и локальный editor-path budget

Запись `user://ember_world_edit_trace_227434733.json` сделана в основной
3D-вкладке Forward+ для `level`, радиус 25 vox, глубина 4: 70 входных шагов,
168 555 реально изменённых voxels за 1,48 с движения курсора. Brush queue
достигла 60, старейший input — 11,35 с; visual pending — максимум 9. Были
кадры с ожидающей кистью при пустой visual queue. Синхронной дублирующей
очереди чанков здесь не доказано: `SurfaceProjection` уже проверяет
`chunk not in _pending`. На каждом кадре `EmberWorldEditor` выполнял только
один `StrokeJob.step(4000)` и уведомлял проекцию после частичного batch write.

Для повторяемого сравнения `tools/fixtures/world_edit_level_real_cells_v1.json`
содержит все 70 клеток и относительные времена той записи. Тест
`tools/qa_world_edit_recorded_brush_queue.gd` подаёт их в очередь того же
`EmberWorldEditor` без пропусков, на плоской карте 14×15 блоков, полностью
охватывающей след кисти. Он подключает рабочий черновик к существующей
`SurfaceProjection` с физикой и запускается в видимом Forward+, но **не**
является автоматизацией главной 3D-вкладки Godot editor. Начальная сборка
карты и прогрев не включены в время жеста. Тест проверяет полный массив
voxels и Undo/Redo, а не только число изменений.

На этой одинаковой записи до → после одной локальной правки:

- очередь 61 → 59; возраст старейшего input median/p95/max
  5,31/10,06/10,57 с → 4,29/8,07/8,44 с (распределение по кадрам,
  когда ещё есть brush job или очередь);
- 70 jobs и 192 736 изменённых voxels в обоих случаях; `step()` 590 → 417;
  итоговый SHA-256 массива совпадает, полные Undo/Redo проходят;
- активное CPU-время brush evaluation 2,30 → 2,28 с, batch prepare

  0,16 → 0,15 с. Эти интервалы не суммируются с wall wait;
