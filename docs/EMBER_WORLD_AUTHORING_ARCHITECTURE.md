# Ember — архитектура authoring мира

Статус: канонический продуктово-технический план будущего **массового**
world-authoring слоя. World Canvas и локальный режим «Редактировать мир» в 3D
уже есть на `main` (`e2084d7`); адресная земля и генератор одной области до
96×96 м реализованы в рабочем дереве. Planners и World Layout ещё впереди.

Обновлено: 2026-10-03.

## Зачем

В Ember уже есть сильные локальные инструменты: Surface Canvas и нативный
3D-редактор с общими черновиками, кисти рельефа и покраски, вода/берег,
библиотека объектов, scene object brush, процедурные деревья, кусты, трава,
камни и другие генеративные источники. Следующий шаг — не делать ещё один
редактор, а поднять эти возможности на уровень больших участков мира.

Цель: автор быстро задаёт намерение — где лес, дорога, река, море, поселение или свободная площадка — получает управляемую заготовку, а затем продолжает редактировать её обычными инструментами вручную.

Главный принцип:

> **Процедурные системы Ember помогают автору построить мир, но не владеют миром после Apply.**

После применения результат становится обычным редактируемым содержимым существующей сцены и существующих Resource owners. Ember не превращается в runtime procedural sandbox.

**Принятая граница для обычной земли:** компактные колонки высоты, материала и
воды становятся единственным источником грунта в переведённой сцене; voxel
Resource остаётся источником объектов и сложной геометрии. Старые сцены могут
сохранять dense Surface до индивидуального решения, но одна сцена не строит
оба варианта грунта одновременно. Первый вертикальный срез подключён в
`scenes/landscape_compact.tscn` и нативном 3D-редакторе; ручная приёмка ещё
открыта. `Agent Sandbox` и боевые арены пока не переводились. Для боёв
компактная земля будет декоративной: хитбокс и правила остаются у клетки
Battlefield, без второй коллизии от декоративного mesh. Текущий gate — в
`EMBER_NOW.md`.

Для обычной земли и базового окружения выбран масштаб 16 ячеек по каждой
горизонтальной оси игрового блока; текущий compact terrain уже работает в нём.
Карта владеет единой сеткой и каналами высоты, цвета и воды. Все scene-owned
карты с `EmberMapLoader.compact_terrain`, включая новые и тестовый берег
`landscape_compact`, используют один
профиль нативного 3D-редактора: основной рельеф объединяет колонки 8×8
(четыре квадратные площадки на блок), средний — 2×2 (8×8 площадок на блок),
детальный редактирует отдельные колонки 16×16. В двух структурных масштабах
отдельная настройка высоты даёт ступень ¼ блока
(4 вокселя) или ½ блока (8 вокселей); каждая половина блока состоит из двух
ступеней по 4 вокселя. Форма следа кисти независимо выбирается
между квадратом и кругом, по умолчанию для основного режима — квадрат. Один
проход по выбранным ячейкам передаёт их кисти, которая меняет нужный канал;
покраска и вода не выравнивают высоту. Это три масштаба authoring над одним
Resource, а не два формата земли или отдельные реализации каждой кисти.
Правка высоты затронутой группы может выровнять ранее нарисованные
мелкие детали внутри неё; выбор масштаба остаётся editor-only состоянием.
При наведении локальная полупрозрачная сетка показывает границы 16×16 и четыре
квадрата 8×8 внутри блока; мягкий контур соответствует радиусу кисти.
В интерфейсе используем однозначные названия: **игровой блок** — 16 единиц,
**ячейка основного рельефа** — группа 8×8 базовых колонок, **полублок высоты** —
8 вокселей, **ступень** — 4 вокселя. Термины «мини-блок» и «под-блок» здесь
не нужны: они смешивают горизонтальный размер ячейки с высотой ступени.
32 voxels/block остаются опцией для отдельных намеренно иных форм и фактур,
например мистических
объектов. Это художественное правило для будущего authoring, а не миграция
существующих voxel Resource или новая глобальная schema. Размеры клетки
Battlefield и правила её хитбокса от этого выбора не меняются.

## Что уже является фундаментом

Новый слой обязан переиспользовать уже принятые границы:

- карта остаётся `.tscn`-сценой;
- voxel-источник объектов остаётся `EmberVoxelModelResource`;
- обычная земля выбирает одного owner на сцену: прежнюю Surface или компактный
  terrain Resource; mesh/collision производны от выбранного источника;
- существующие генераторы единичных объектов не переписываются в новый формат;
- preview должен соответствовать Apply;
- тяжёлая операция применяется одной логической Undo/Redo-командой;
- после Apply отдельные созданные объекты можно вручную двигать, удалять и редактировать обычным путём;
- одна сцена не получает второй активный renderer грунта или параллельный voxel editor;
  compact Save проходит через существующую транзакцию редактора сцены.

Любой конкретный implementation contract сначала обязан найти существующих owners в коде и доказать, что нужную задачу нельзя выразить через них.

## Четыре уровня

### 1. Generator — создать одну вещь

Generator отвечает только за форму одного элемента или одного типа поверхности.

Уже существующие примеры:

- дерево;
- куст;
- трава;
- камень;
- кристаллические/скальные формы;
- локальный рельеф;
- берег/дно и вода в уже принятой системе Surface.

Будущий пример — генератор простого объёма здания.

Generator не должен самостоятельно решать, где находится лес, квартал или дорога. Он получает конкретные параметры и создаёт конкретный результат.

### 2. Planner — решить, что и где разместить

Planner использует один или несколько существующих generators/recipes и строит план размещения внутри заданной области.

Примеры:

- роща из нескольких рецептов деревьев;
- лес с подлеском, кустами, камнями и свободными окнами;
- набор камней вдоль берега;
- квартал из нескольких building massing-рецептов.

Planner работает детерминированно от seed, учитывает ограничения области и сначала создаёт preview plan. До Apply каноническая сцена/Surface не меняются.

### 3. World Layout — выразить намерение автора

World Layout — семантический слой поверх сцены. Он не заменяет карту и не становится новым runtime-миром.

Предполагаемые примитивы:

**Линии / сплайны**

- `Road` — дорога или тропа;
- `River` — русло/направление реки;
- другие линейные authoring-намерения добавляются только по реальной задаче.

**Области**

- `Forest / Biome` — участок природного наполнения;
- `Sea / Water Area` — большая водная область/ориентир для подготовки берега и воды;
- `Settlement` — область поселения;
- `Clearing` — намеренно свободное пространство;
- `Reserved` — участок, который planners не должны занимать автоматически.

**Точки / якоря**

- landmark;
- мост/место перехода;
- вход в данж или другое важное авторское место;
- точные типы добавляются только тогда, когда появляется конкретный потребитель.

**Запреты**

- `NoBuildings`;
- `NoVegetation`;
- `Reserved` или другой явный exclusion mask.

Названия выше пока являются design contract, а не утверждённой schema. Перед кодом нужно выбрать минимального owner и формат без дублирования существующей сцены.

### 4. Apply / Authoring — материализовать результат

Planner выдаёт план, а authoring-слой показывает его в сцене и применяет через существующих owners.

Правила:

- Preview не изменяет канонические данные.
- `Apply` — одна логическая операция Undo/Redo на согласованный срез.
- Save/Reopen воспроизводит уже применённый обычный контент, а не требует повторно запускать planner.
- После Apply результат не обязан оставаться связанным с исходным planner-рецептом.
- Повторная генерация существующего участка всегда должна быть явным действием, а не скрытым live-update.
- Никакой runtime-генерации только потому, что authoring использует seed.

## Seed и управляемая случайность

Случайность должна быть воспроизводимой и раздельно управляемой.

Предпочтительная модель — иерархический seed:

`world/region seed → planner seed → layer seed → generator seed`.

Практический эффект: автор может получить другой набор камней, не меняя удачную раскладку деревьев; или перегенерировать кусты, сохранив рельеф и дороги.

Для первого среза не нужна сложная система наследования seed в данных. Важен контракт: разные слои не должны случайно менять друг друга из-за одного глобального reroll.

## Preview и обратимость

Будущие world-инструменты продолжают уже знакомый UX Ember:

1. автор задаёт область/линию и параметры;
2. система показывает draft/preview;
3. seed и параметры можно менять без мутации сцены;
4. `Apply` создаёт результат;
5. один Undo возвращает состояние до Apply;
6. Save/Reopen сохраняет результат;
7. дальше автор правит его обычными ручными инструментами.

Для больших участков preview может быть упрощённым, но Apply не должен неожиданно менять композиционный смысл по сравнению с preview.

Первый кандидат пресета новой карты даёт ровную травяную землю через
«+ Карта» в нативной 3D-панели. Он создаёт отдельную сцену и компактный Resource;
параметры до явного создания меняют только подготовленный в памяти источник и
дешёвый вид сверху. Ctrl+Z не удаляет созданные файлы; последующие мазки входят
в обычную историю редактора. Живая приёмка этого потока открыта.
Для первого теста большого мира один авторский участок означает 24×24 игровых
блока. Выбор 1–4 участков при создании и добавление одного по краю меняют размер
того же scene-owned terrain Resource; рельеф, материалы и текущая жидкость остаются у него.
Добавление участка по умолчанию делает ровное продолжение с коротким переходом
от соседней границы; прежнее копирование края выбирается отдельно. Временный 3D
preview использует геометрию той же кандидатной земли, которую применит Apply.
Параметр жидкости в authoring понимается как тип и уровень; сегодня доступна
только вода, а новые типы потребуют отдельного контракта на Resource/schema.
Участок пока служит единицей authoring, а не отдельным загружаемым Resource:
решение о потоковой загрузке требует замеров больших сцен с объектами.

Первый пресет берега добавлен в «+ Карта» рядом с ровной землёй: высота суши,
уровень нынешней воды, величина неровностей и seed задают квадратные площадки
8×8 колонок со ступенью 4 вокселя, песок у воды и траву выше. Вся карта
считается одним полем по её координатам, поэтому границы авторских участков не
вводят шов. Вид сверху берётся из подготовленного в памяти Resource; явное
создание записывает эти же данные в сцену и compact terrain Resource, не
запекает их обратно в dense Surface. Рецепт пока не сохраняется для повторной
генерации уже созданной карты: результат дальше редактируется штатными кистями.
Вариации отдельных voxel-объектов остаются у существующего генератора объектов.
Повторная генерация участка, новые типы жидкости и семантические материалы
требуют отдельных решений. Ручная оценка рисунка берега ещё открыта.

## Большая карта как управляемый план областей

**Текущий запрос и результат исследования:** автор выбрал ориентир первых
больших островов **256–512 м**, затем увеличение по замерам. Масштаб остаётся
1 игровой блок = 1 м = 16 колонок по оси; персонажи около 2 м не увеличиваются
вместе с картой. Приёмка материалов отложена по просьбе автора, её результат
и ограничения остаются в `EMBER_TERRAIN_AUTHORING.md`. Генератор одной области
реализован; Layout ещё впереди. Контракт на адресные участки реализован:
часть края/пустой адрес, общий terrain owner, native preview/Undo/Save и F6.
Детальная авторская приёмка и заполненный масштаб ещё открыты.

Исследование действующего кода выявило ограничения, которые нельзя скрывать
за увеличением ползунка размера:

- `EmberTerrainPilotResource` сохраняет чтение плотной schema 1; schema 2
  хранит шесть каналов только созданных участков внутри того же Resource:
  две Int32-высоты и четыре byte-канала, суммарно 12 байт на колонку.
  Для полностью заполненных 256×256 м это около 192 MiB, для 512×512 м —
  768 MiB только исходных каналов. Это расчёт, не замер памяти процесса;
  поток воды, исключения, черновик, baseline, Undo, mesh, физика и поля воды
  добавляют расход. Черновик schema 2 разделяет неизменные payloads;
  запись копирует только затронутые участки, Undo сохраняет их версии.
- «+ Карта» начинает с 1–4 участков по оси (до 96 м). «+ Участок» включает
  выбор в 3D: щелчок — один квадрат, протягивание — прямоугольник до 4×4
  участков. Затем та же цепочка открывает рельеф/уровень воды, exact preview
  и Apply. Уже созданные участки в выделении сохраняются; новые получают общий
  рисунок генерации и переход к прежней земле. Бюджет адресов —
  22×22 (оболочка 528 м); пустые адреса не материализуются. Плитки прежнего
  renderer по 64 колонки (4 м) собираются только для созданных участков.
  Внутренний tile читает один payload, шов — небольшое окно с соседями;
  прежние внутренние tile/коллизия сохраняются при добавлении участка.
- Новая карта получает `height_limit = 128`, то есть диапазон 8 м относительно
  её основания. Генератор гор потребует отдельного управления диапазоном и
  абсолютными высотами, без изменения размера персонажа/блока. Int32-каналы
  уже позволяют больший диапазон; стоимость склонов/физики ещё надо измерить.
- Уровень воды уже хранится по колонкам, поток — по игровым блокам. Разные
  высоты озёр выразимы текущими данными. Проба `EmberCompactWaterfall` выбирает
  один основной перепад; несколько водопадов, связанные водоёмы и область
  морского прибоя пока не являются доказанным общим authoring-потоком.
- Picking/физическая высота читают адресный terrain; navigation снимает высоты
  только с созданных участков, оставляя компактную сетку игровых блоков.
  Save/Reopen/Discard и baseline используют тот же owner. Производные поля
  сложной пробной воды теперь региональные: созданный участок и halo, общий
  граф морской связности, фоновые CPU данные и постепенная загрузка материалов.
  Контрольный рост до 192×120 м проверен; предел данных совпадает с оболочкой
  terrain, но заполненные 256–512 м этим не принимаются. Текущие owners,
  измерения и ограничения — Water Rendering → «Действующий путь пробы».

Участки экономят пустые адреса и ограничивают правку/Undo, но не делают
полностью заполненный остров автоматически дешёвым. Решение о загрузке
ближних участков и меньшей детализации дальних принимается по замерам
заполненной карты с объектами; оно не добавляет второго источника земли.
В Ember блок сейчас занимает 16 единиц Godot: 512 м — 8192 единицы по оси.
Перед дальнейшим ростом проверять физику/дрожание вдали от начала координат;
смена единиц или double-precision сборка не входят в первый срез.

**Проверенный результат основы:** `test_compact_map_sections` сохраняет все
шесть прежних каналов, flow и боковые исключения, проверяет неполный край,
свободные адреса, Undo кисти/толщины верхнего слоя, Save/Reopen/Discard,
физику и navigation у шва и на далёком участке. Шесть участков в оболочке
528 м дают 216 tile, а не полную сетку 484 участков. Native Forward+ fixture
проверил preview/cancel/Apply, геометрическое совпадение, западный сдвиг,
пустой адрес, общий EditorUndoRedoManager, Save/Reopen/Discard и настоящий F6
с проходом персонажа через стык. Ровная 96×96 м: headless сборка 576 tile
~0,91 с, худший измеренный кадр ~7 мс; это не замер live input и не слабый ПК.
Авторская оценка интерфейса, заполненный остров 256–512 м, recovery после
аварии на такой карте и потоковая загрузка остаются открытыми.

**Действующий вход добавления участков:** «+ Участок» → выбор места в 3D
по сетке 24×24 м → «Далее: рельеф и вода» (Enter) → параметры → предпросмотр →
«Добавить участки». Синие квадраты будут созданы, серые уже существуют.
Общее окно генерации закрывается только после успешного commit; автоматическое
закрытие AcceptDialog перед `confirmed` отключено. Отказ остаётся виден в окне,
а устаревший предпросмотр требует повторной подготовки.
«Изменить выделение» возвращает к той же области; Esc/отмена не меняют землю.
На этом шаге лишние верхние кнопки временно скрыты; параметры прокручиваются
в ограниченном окне. Новая область остаётся выбранной для кистей.
Владелец выбора/истории — прежний WorldEditor; чистый
`ember_compact_section_selection.gd` считает адреса/смещение/бюджет, прежний
generation job готовит только отсутствующие payloads. При росте слева/сверху
scene transform Map компенсирует перенос адресов, а группы получают обратный
сдвиг: прежние объекты и физическая земля сохраняют мировые позиции.
Undo, Save/Reopen, Discard и editor recovery учитывают эту расстановку;
сохранение снимает временный preview до сериализации. Новая schema не вводится.
Native Forward+ проверил мышь/Enter/Back/Esc/камеру, занятые и смешанные области,
настоящую OK-кнопку и видимый отказ применения, preview=Apply, единый Undo/Redo,
оба пути Save с открытым preview, Discard,
Reopen и F6 с коллизией новой земли. Панель/окно проверены при 125% в 1600×900
и 1280×750. Художественная оценка стыка и удобство автора ещё OPEN.
Переделка «+ Карта», свободный контур и сохраняемая разметка — следующие
отдельные решения; новый путь не создаёт сохранённого Layout.

Цель следующего уровня — автор сначала размечает крупные части сцены, а затем
создаёт их содержимое. Например: островная суша, берег вокруг неё, высокая
каменистая область, ровное место для поселения, дорога и несколько областей
растительности. Простая случайная вариация уточняет заданную автором форму, но
не выбирает за него место города или путь дороги. Область может занимать часть
одного участка или несколько участков 24×24 блока; участок остаётся единицей
хранения и обновления земли, а не границей замысла автора.

План — authoring-данные сцены, которые можно сохранить и открыть снова до
применения. Его точный scene-owned owner и формат выбираются в отдельном
вертикальном контракте. После Apply высоты, покрытия и жидкость принадлежат
единственному compact terrain Resource карты, а созданные деревья и камни —
существующим scene/voxel owners. Сохранённый план не является вторым источником
физической земли: изменение параметра плана само по себе не меняет применённую
карту. Повторное применение к уже нарисованной области требует явного действия
и понятного предупреждения о ручных правках, которые оно заменит.

### Примитивы и порядок влияния

Действующий генератор одной области: существующее editor-only `edit_region`
выбирает прямоугольник до 96×96 м; `ember_terrain_generation_math.gd` владеет
sampling острова/холмов/хребтов/приближения эрозии и совместимым прежним берегом.
`ember_compact_terrain_generation.gd` готовит по участкам приватный candidate
того же terrain Resource. WorldEditor применяет его через общую сессию и Undo;
прежний candidate preview использует тот же mesher. Координаты шума общие для
области, стыки участков не перезапускают seed. Внешняя земля сохраняется,
storage ceiling увеличивается отдельно от физических высот. Тот же job в пути
«+ Участок» создаёт только новые участки, сохраняя занятые и их поток/материалы;
параметры общие для выделенной области. Native/F6 прошли,
авторская оценка открыта; параметры ещё не являются сохраняемым планом.
Подробное действующее поведение и ограничения — Terrain Authoring →
«Генератор рельефа выбранной области». Список ниже остаётся направлением Layout,
а не утверждением о наличии всех этих компонентов.

- **План сцены** хранит границы/линии, именованные намерения, параметры и seed;
  его UI редактирует план и запрашивает preview. Он не вычисляет физическую
  высоту отдельно от terrain и не перегенерирует мир при F6.
- **Область суши/острова** задаёт границу земли и воды; берег добавляет
  управляемую переходную полосу, а не отдельный renderer.
- **Область рельефа** задаёт возвышенность, склон или ровную площадку. Гора —
  высокий профиль рельефа, не набор случайно поставленных мелких столбиков.
- **Водная область и направленное русло** задают море/озеро со своим уровнем,
  дно, вход/выход и связь рек с водоёмами. Водная подготовка вырезает русло и
  записывает уровни/поток через тот же terrain owner; берег/перепад и эффекты
  остаются производными. Одна общая установка уровня моря не выравнивает
  горное озеро. Маршрут реки и перепад проверяются до Apply; полномасштабная
  симуляция эрозии/жидкости не является требованием первого генератора.
- **Линия дороги** резервирует коридор, задаёт ширину и допустимый уклон,
  затем обращается к существующим операциям высоты и покрытия.
- **Область наполнения** задаёт, где позже могут появиться деревья, трава,
  отдельные камни и их группы. «Каменистая область» и конкретный камень-якорь
  являются разными авторскими намерениями.
- **Свободная/зарезервированная область** запрещает автоматическое наполнение
  и оставляет место для ручной постройки.

На пересечениях первыми учитываются явные запреты и коридоры дорог, затем
форма земли и воды, после них покрытие и размещение объектов. Это правило
должно быть показано в preview и проверено на реальных пересечениях; точные
приоритеты типов не фиксируются в schema до такого среза.

Суша/рельеф и подготовка воды используют общую чистую математику sampling в
координатах карты: граница участка не перезапускает случайную последовательность.
Покрытия выбирают существующие семантические материалы по готовой земле,
уклону и воде, а planner наполнения использует прежние object recipes.
Лес/пустыня/поле — будущие сочетания покрытия и наполнения с раздельными seed,
не новые terrain/render owners. Изменение слоя камней не меняет высоту горы.

### Параметры без путаницы масштаба

Параметры разделяются по тому, что они меняют:

- **Размер карты/области:** сколько участков существует и какую часть карты
  занимает конкретная область. Это не размер ступени и не частота шума.
- **Форма рельефа:** базовая высота, амплитуда, ширина склона/берега, размер
  крупных особенностей по горизонтали, степень мелкой вариации и шаг высоты
  действующего профиля карты. Горизонтальный масштаб определяет, насколько
  широки холмы и изгибы, не увеличивая плотность колонок всей карты.
- **Вода:** тип жидкости, уровень и связь с берегом. Сейчас реализована только
  вода; другие жидкости остаются отдельным контрактом данных и изображения.
- **Покрытие:** начальный смысловой слой compact terrain связывает слот палитры
  с ролью грунта, травы, песка или камня. Старые карты без такой роли не
  переосмысляются по цвету автоматически. Именованные общие паттерны
  16×16 с тремя тонами выводятся через существующий compact terrain mesh;
  два слота одной роли позволяют рисовать разными вариантами рядом;
  художественная приёмка
  открыта. Будущий отдельный визуальный срез может дать ступенчатые переходы
  трава↔грунт и трава↔песок, редкие цветовые варианты блоков и мох на камне;
  конкретное правило смешивания и место его хранения ещё не выбраны. Роли
  также служат основой для правил переходов и будущего
  генератора, но не задают реакцию стихии. Общая визуальная библиотека
  материалов согласуется в отдельной графической работе.
- **Наполнение:** набор существующих object recipes, плотность, минимальный
  интервал, группирование, ориентация и маски запретов. Плотность объектов не
  меняет разрешение земли.
- **Случайность:** seed карты, области и отдельного слоя. Новый рисунок камней
  не должен менять удачный берег, дорогу или деревья.

В интерфейсе эти настройки идут по уровням **карта → выбранная область →
слой → дополнительные параметры**. Размер области и масштаб форм видны
раздельно; автор не должен разбирать один длинный список одинаковых «частот»,
«плотностей» и числовых цветов. Значения рядом с ползунком остаются точными,
а для большого размера предусмотрено редактирование границы прямо в 3D.

Значения параметров сначала показывают результат в дешёвом общем плане карты и
в локальном 3D-preview выбранной области. Preview берёт ту же детерминированную
математику и те же material/recipe references, что Apply. Большая область
готовится и применяется по затронутым участкам с прогрессом и отменой; один
Apply остаётся одной логической Undo-командой. Нельзя перестраивать всю карту
при каждом движении ползунка. Уже вручную изменённые участки и соседние швы
должны быть видны до подтверждения замены.

Масштаб проверяется ступенями: сначала один участок и пересечение границы,
затем текущая карта 4×4/5×4, затем карта больше неё с несколькими разными
областями и репрезентативными объектами. Время подготовки, худший кадр,
потребление памяти, число tile/draw calls, скорость кисти и Save/Reopen
измеряются отдельно. Верхний размер карты и целевое время Apply назначаются
по этим замерам и живой приёмке, а не исходя из нынешнего ограничения диалога
на 4×4. Пустые будущие адреса участков не выделяют колонки, mesh и collision.

Для методов формы рекомендуются контур автора и профиль склонов/хребта,
которые управляют основным силуэтом; FastNoiseLite уточняет крупные и мелкие
неровности с раздельными масштабами и seed. Искажение координат может убирать
регулярность, но не определяет за автора берег, русло или место дороги.
Это рекомендация для будущего генератора, не уже выбранная реализация.
Источники исследования: [FastNoiseLite в Godot 4.7](https://docs.godotengine.org/en/4.7/classes/class_fastnoiselite.html),
[управляемый рельеф и речная сеть](https://perso.liris.cnrs.fr/apeytavi/website/publication/hal-01262376/),
[точность больших координат](https://docs.godotengine.org/en/4.7/tutorials/physics/large_world_coordinates.html).
Из исследований берётся принцип управляемой формы и связей воды; их сложная
эрозия не переносится в Ember автоматически.

## Первый object-planner vertical slice: роща

Первый planner размещения объектов следует делать маленьким. Не начинать с
полного биома или города.

### Goal

Выделить область в 3D-мире и быстро получить редактируемую рощу из уже существующих object recipes.

### Минимальный пользовательский поток

1. Выбрать или нарисовать область.
2. Выбрать несколько существующих рецептов деревьев; опционально кусты и камни.
3. Настроить плотность/минимальный интервал и seed; учесть воду, уклон и
   зарезервированные дорожные/строительные коридоры.
4. Увидеть preview расстановки.
5. Нажать `Другой вариант`, не меняя саму область.
6. `Apply`.
7. Проверить одну Undo/Redo-команду.
8. Save/Reopen.
9. Вручную сдвинуть, удалить или отредактировать отдельное созданное дерево обычным способом.

### Что этот срез должен доказать

- массовая расстановка не создаёт второго owner объектов;
- существующие generators действительно можно использовать как leaf-уровень;
- preview достаточно быстрый для авторской работы;
- seed воспроизводим;
- размещение проверяет ту же высоту и воду, что используют игрок и AI;
- после Apply мир остаётся обычной редактируемой сценой;
- exclusion/spacing можно добавить без переписывания generators.

### Что не входит

- полноценные биомы;
- дороги и реки;
- автоматический рельеф под лес;
- сезоны/ветер;
- автоматический город;
- runtime procedural generation.

## 3D world brushes

Отдельный ближайший слой — перенос уже созданной грамматики кистей на больший масштаб прямо в основной 3D-вкладке.

Задача не в том, чтобы копировать весь Surface Canvas второй раз. Нужно определить, какие существующие операции действительно полезны на уровне карты: крупный рельеф, сглаживание, берег/дно, покраска, маски/области и placement.

Первый technical contract 3D world brushes должен:

- измерить текущие owners и стоимость больших операций;
- переиспользовать чистую математику существующих кистей;
- не создавать второй Surface/brush state;
- иметь draft/preview и bounded Apply;
- работать на representative map, а не только на маленьком тестовом объекте;
- сохранить Undo/Redo, Save/Reopen и текущий Forward+ visual result.

## Биом как planner, а не generator

`Biome` — композиция нескольких слоёв, а не новый генератор «всего мира».

Возможные слои будущего биома:

- основные деревья;
- вторичные деревья;
- кусты/подлесок;
- трава/низкая растительность;
- камни/кристаллы;
- редкие акценты;
- свободные окна и exclusion-зоны.

Каждый слой использует собственный набор существующих recipes и независимый seed. Биом отвечает за правила распределения и композицию, а не за геометрию каждого дерева или камня.

Сначала роща должна доказать placement foundation. Только после этого имеет смысл расширять её в Biome Planner.

## Дороги, реки и море

Линейные и водные структуры должны исходить из World Layout, а не возникать как случайный шум.

Предпочтительный порядок:

1. автор задаёт линию/область;
2. инструмент строит preview требуемого изменения Surface/placement;
3. существующие кисти рельефа, покраски, берега/дна и воды выполняют leaf-операции;
4. Apply фиксирует результат через их owners.

`River` не должен становиться отдельным вторым типом карты. Аналогично `Sea Area` — это authoring intent для существующей системы берега/дна/воды, а не новый water renderer.

Для реки, прибоя и будущего водопада действует один источник формы воды:
уровень и дно принадлежат карте, направление потока задаётся для мокрой области,
а расстояние и нормаль берега выводятся из карты после Apply. Одна высота и
наклон движущейся поверхности должны согласованно управлять mesh, преломлением,
отражением и контактом объектов. У моря широкий нерегулярный фронт идёт к
берегу, на мелководье формирует локальную пену, набег и откат; у реки рисунок
движется по изгибу русла, слабее у берегов. Водопад добавит вертикальный участок
между верхним и нижним уровнями, сохраняя того же владельца воды и локальные
волны в бассейне удара. Взаимодействие с объектами использует существующий
`EmberWaterContact3D`; визуальное течение не обязано сразу толкать героя.
Порядок проб: русло и поток → береговая реакция и пена → контакт объектов →
водопад. Каждый шаг проверяется в Forward+ и оценивается в движении до переноса
на авторские карты.

## Building Massing v0

Генератор здания начинается не с «умного дома», а с управляемого силуэта.

Первый договорённый уровень:

- footprint;
- количество этажей;
- общая высота и пропорции;
- простой основной объём;
- форма крыши;
- лёгкое членение фасада;
- простые проёмы только если они не требуют новой сложной архитектуры.

Результат — обычный редактируемый объект/набор объектов существующей voxel-системы.

Не входят в v0:

- интерьер;
- назначение комнат;
- мебель;
- NPC/расписания;
- procedural quest logic;
- автоматическая навигация между этажами;
- полноценные архитектурные стили города;
- генерация целого поселения одним нажатием.

После художественной приёмки massing один Settlement Planner сможет использовать несколько таких recipes для квартала. Не наоборот.

## Settlement / City Planner — позже

Поселение — planner высокого уровня. Оно должно учитывать как минимум:

- World Layout дорог/площадей;
- `NoBuildings` и reserved areas;
- landmarks;
- набор building massing-рецептов;
- интервалы и ориентацию относительно улиц;
- свободное место для ручного authoring.

До появления рабочего building massing и line/area layout этот слой не реализуется.

## Порядок развития

Рекомендуемая последовательность:

1. **Закрыть живую опору.** Проверить берег, большую кисть, Undo/Redo,
   Save/Reopen и 3D-просмотр на текущей 4×4/5×4 карте. Сопоставить замеры
   ввода, генерации, построения плиток и кадров; не объявлять отдельный
   Forward+ профиль скоростью редактора. По просьбе автора исследование
   большой карты начато до завершения художественной приёмки материалов;
   незакрытые gates сохранены в NOW и не считаются пройденными.
2. **Сделать карту адресуемой по участкам.** По уже выбранному направлению один
   scene-owned compact Resource хранит данные только созданных участков
   24×24 блока. Старые карты должны открываться без потерь. Добавление
   прямоугольника у части края, швы, кисти через границу, физика, preview,
   Undo и Save закрываются одним вертикальным срезом. Пустая координатная
   сетка не материализуется заранее. Основа реализована 2026-10-03;
   автоматические/native QA и F6 прошли, авторская приёмка ещё открыта.
3. **Параметризовать генератор рельефа.** Вынести форму нынешнего берега в
   воспроизводимый расчёт с раздельными размером области, горизонтальным
   масштабом особенностей, высотой, шириной берега, уровнем воды и seed.
   Сначала одна выбранная область и preview→Apply в тот же terrain Resource;
   существующий результат после применения можно править кистями. Замеры
   охватывают область через несколько участков и её соседей. Срез одной области
   реализован: холмы/хребты/изрезанные склоны, существующее выделение, preview→Apply,
   общий sampler, Undo/Save и F6. Авторская приёмка и большие размеры OPEN.
4. **Ввести минимальный World Layout.** Сохраняемая разметка нескольких
   областей задаёт остров/сушу, берег, гору или возвышенность и свободную
   площадку. Preview показывает границы, пересечения и порядок слоёв.
   Применение затрагивает выбранные участки, а не перерисовывает всю карту.
5. **Водные связи.** Сначала море и одно озеро выше моря, затем редактируемое
   русло между уровнями и один явный водопад. Проверить сохранённые уровни,
   стыки, физику и текущие эффекты в 3D/F6; следующий отдельный gate — несколько
   связанных водоёмов/перепадов. Подготовка данных воды и её изображения
   сохраняет нынешних owners; море не заливает любое углубление только потому,
   что оно ниже уровня моря. Точное правило связи/ограничения выбирается
   контрактом воды, не этим планом.
6. **Первый planner объектов.** Роща и отдельный слой камней используют
   существующие object recipes; автор настраивает плотность, интервалы,
   группирование, exclusion и отдельные seed. После Apply каждый объект
   редактируется прежними инструментами. Лишь затем расширять эти правила
   до полного биома.
7. **Дорога и расширение биомов.** Дорога/тропа резервирует коридор, задаёт
   уклон и покрытие. Лес, пустыня и поле расширяют проверенные правила рощи
   и покрытия. Точные пересечения с водой/областями проходят отдельную приёмку.
8. **Более высокие композиции.** Building Massing v0, затем Settlement
   Planner с дорогами, площадками и ручными ориентирами. Не начинать с
   автоматического города одним нажатием.

Базовые роли грунта, песка, травы и камня уже есть в compact terrain;
генератор использует их существующую библиотеку. Новые материалы и жидкости
требуют отдельного решения; форма областей не подменяет их числовыми
«Цвет 1/2/3». На каждом этапе проверять
карту больше 4×4 и полную стоимость preview, Apply, открытия, Undo и живых
кадров; при достижении нового масштаба отдельно решать подгрузку плиток около
камеры по измерениям. Это сквозная граница, а не обещание бесконечной карты.

Порядок можно менять после измерений и ручной проверки; он не является обязательством реализовать всё подряд.

## Производные данные и стоимость эффектов

Эти правила продолжают нынешних owners; отдельный общий менеджер эффектов
этим решением не введён. Авторский результат и параметры сохраняются в прежних
scene/Resources. Береговые расстояния, mesh, поля движения и другие вычисляемые
данные принадлежат их производному пути и не становятся вторым источником мира.

- Неизменные данные готовятся при появлении/изменении источника. Новые эффекты
  должны явно указывать ключ зависимости, область invalidation и момент
  пересчёта; изменение одного участка не оправдывает обход всей большой карты.
  Пробный берег переиспользует неизменные региональные поля; смена морской
  связности может затронуть дальние регионы, общий flow/phase остаётся coarse.
- Визуальная анимация использует GPU, когда это уменьшает измеренную стоимость.
  История пены/влажности остаётся на GPU; CPU запрашивает нужные физике точки
  общей математикой. Не переносить большие поля CPU↔GPU каждый кадр ради этих
  точек и не пересчитывать неподвижный preview без изменения входов.
- Производный кэш в памяти нужен повторным обращениям. Постоянное запекание
  добавляется, если замер доказывает пользу подготовки/открытия: ключ включает
  версию алгоритма и значимые исходные данные, повреждение/устаревание требует
  пересборки, кэш можно удалить без потери авторской карты. Динамическую историю
  каждого кадра на диск не писать. Узкий кэш статических береговых полей по участкам
  реализован; действующий результат/граничные случаи — Water Rendering →
  «Действующий путь пробы». Runtime-кэш точной земли/воды и их LOD реализован
  отдельным производным owner; запекание всего мира пока не реализовано.
- Понижение мелких деталей воды по расстоянию и runtime LOD земли/воды реализованы;
  выключение невидимых эффектов — отдельный срез по замерам. Физическая
  поверхность остаётся общей; упрощённая
  дальняя картинка не меняет высоту/коллизию под персонажем. Универсальный LOD
  и streaming пока не реализованы.
- Каждый новый эффект проверяется на растущей репрезентативной карте: отдельно
  подготовка, повторное обновление CPU, GPU, draw calls и общий кадр активной
  вкладки 3D/F6. Замер включает состояние без действий, изменение параметров,
  локальную правку, Undo/Save/Reopen и освобождение ресурсов. Маленькая fixture
  и мощный ПК не закрывают большие карты/слабое устройство.

Первый подтверждённый пример — GPU-история морского набега без смены renderer,
mesh или авторского Resource. Действующие замеры и оставшиеся gates принадлежат
`EMBER_WATER_RENDERING.md` → «Морской набег и мокрый песок».

Предложенный порядок оптимизации больших карт (2026-10-05), по просьбе автора:
сначала земля, затем вода. Это очередь отдельных проверяемых срезов, не общий
согласованный контракт реализации. Исходный native baseline и стоимость сборки —
Terrain Authoring → «Производительность и границы доказательств».
Уточнённая автором граница: новые геометрические упрощения/LOD и запечённые
игровые варианты предназначены для runtime, не для перестройки карты на каждой
editor-правке. Редактируемый источник и локальный быстрый mesher сохраняются;
runtime результат выводится из этого источника в текущем renderer. Работа над
игровой оптимизацией не оправдывает ухудшения ввода/кисти редактора.

1. **Земля без потери формы.** Проверить уже работающие объединение площадок и
   удаление внутренних граней; уменьшать только доказанную избыточную геометрию
   и работу сборщика. Сохранять ступени, материалы и одну физическую поверхность.
   Если текущий mesher уже минимален на проверенной форме, не вводить замену ради
   формального выполнения этапа. Срез согласован и реализован: одинаковые
   соседние side bands объединяются существующим mesher только в runtime;
   editor вернулся на непосредственные side quads. Native команды/F6
   прошли; действующие замеры и ручная приёмка — Terrain Authoring.
2. **Дальняя земля.** Проверить геометрический LOD по участкам: подробный ближний
   вид, простые дальние формы, стабильные стыки и силуэт. Физика под персонажем
   использует прежнюю поверхность, а не дальнюю картинку. Срез согласован и
   реализован только в runtime: один worker готовит индексы прежнего ArrayMesh
   во время загрузки, native screen-error LOD выбирает готовый уровень без remesh.
   Editor jobs отсутствуют; исходные границы tile и физика точные. Замеры,
   консервативный fallback и открытая визуальная приёмка — Terrain Authoring.
3. **Вода без потери вида.** Измеренно уменьшать стоимость статических water
   walls/stitching и избыточную плотность сетки. Сохранять речную/морскую волну,
   берег, набег, водопад и совпадение стыков; визуальное упрощение сюда не входит.
   Первый точный runtime-срез реализован: indexed ArrayMesh объединяет одинаковые
   vertices/attributes, временный cache исключает повторный depth sample внутри
   build_tile. Triangles/order и плотность прежние; editor не выполняет эти работы.
   Действующие замеры и открытая F6-приёмка — Water Rendering.
4. **Дальняя вода.** Реализован runtime-only far index buffer внутри 1м patches,
   с сохранением shallow/depth/material transitions, shoreline/walls/sheet и стыков.
   Общий worker земли/воды работает при загрузке; native LOD не требует remesh
   камеры. Near arrays и physics точные, editor jobs отсутствуют. Native дальний
   primitives −18,6%, GPU около −7,8%, старт дольше на 3,7 с. Подробные замеры,
   стоимость памяти, fallback и открытая авторская приёмка — Water Rendering.
5. **Кэш готовой геометрии.** Сохранять проверенные результаты земли/воды и LOD
   как удаляемые производные данные с version/content/dependency key. При локальной
   правке пересчитать нужные зависимости; повреждение/отсутствие требует обычной
   сборки. Ограничить диск и память, измерить cold/warm startup. Береговой кэш
   продолжает своего owner; покадровая GPU-история не сохраняется. Реализован
   только в runtime: geometry arrays/точные collision faces и отдельные LOD indices
   в `user://ember-terrain-geometry-cache`. Ключ включает версию алгоритма/Godot,
   palette/origin, runtime policy, содержимое tile и соседнего кольца 3×3,
   swash/falling-sheet geometry. Рост карты не инвалидирует дальние tiles;
   локальная правка пересобирает консервативный набор соседей, Undo возвращает
   прежний ключ. Files атомарные, Zstd/checksum, до 16 MiB на запись и 512 MiB
   после фоновой очистки batch. Shared worker читает/сохраняет LOD; near geometry
   восстанавливается/записывается по tile в прежней очереди. Нет финальной массовой
   записи всей карты, нового renderer или authoring schema. Повреждение/ошибка I/O
   возвращает обычную сборку. Подробные замеры/ограничения — Terrain Authoring.
6. **Видимость и загрузка по участкам — по замерам.** Если после предыдущих срезов
   остаётся значимый расход CPU/памяти/старта, отдельно согласовать остановку
   невидимых эффектов и streaming. Само скрытие mesh не останавливает effect CPU;
   готовность физики и активных игровых объектов обязательна.

После каждого среза сравнить одинаковую fixture до/после: время подготовки,
геометрия, CPU/GPU/кадр, память и стабильность. Editor-изменения закрыть через
Undo/Redo/Discard, Save/Reopen и native 3D/F6; визуальная приёмка остаётся за автором.
Рост от 192×120 м к заполненным 256–512 м проверять постепенно; мощный ПК не
закрывает слабое устройство. Ближайшее действие — авторская приёмка игрового LOD
земли; остаточную задержку editor-кисти автор отложил, gate остаётся открытым.
Точная и дальняя водная geometry реализованы и также ожидают авторского F6.
Кэш geometry/LOD реализован, автоматические и native проверки пройдены;
авторский повторный F6 после Save/локальной правки/Undo OPEN. Следующий отдельный
контракт — оценка невидимых участков и загрузки по расстоянию по пункту 6;
visibility/streaming не начаты и не считаются обязательными без замеров.

## Неподвижные границы

- Не создавать дополнительный формат мира поверх существующих scene-owned
  terrain и voxel Resource.
- Не создавать новый renderer/mesher только ради planners.
- Не встраивать orchestration леса/биома внутрь генератора дерева.
- Не делать live procedural world, который перегенерируется при загрузке игры.
- Не скрывать большой Apply без preview и Undo.
- Не считать generator output финальным артом: авторская ручная правка остаётся нормальной частью процесса.
- Не смешивать в одном первом контракте лес, дороги, воду, дома и поселение.
- Любой новый authoring Resource сначала получает одного явного owner и правила Save/Reopen.

## Открытые решения перед кодом следующих срезов

Адресная основа использует совместимую schema 2 в прежнем compact Resource;
старый файл не переписывается при открытии, переход сохраняется явным Save.
Генератор одной области сохраняет внешние правки и использует явный preview→Apply;
диапазон высот расширяется метаданными под параметры рельефа, общий уровень
моря задаётся отдельно. Авторская приёмка формы/склонов ещё открыта.
Для первого редактируемого плана области — выбрать минимальную форму области
(прямоугольник или произвольный контур), scene-owned место хранения плана,
вид 3D-preview и правило сохранения ручных правок при повторном Apply.
Для Grove/камней затем согласовать lightweight preview десятков/сотен объектов,
spacing, exclusions и доступ к существующей библиотеке без её копирования.
Эти решения принимаются отдельными Task Contracts; данный план не вводит
новую schema сам по себе.
