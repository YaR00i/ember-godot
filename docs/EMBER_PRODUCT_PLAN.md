# Ember — продуктовый план

Продуктовая последовательность уточнена 2026-09-30.
Этот документ хранит долговечное видение, масштаб и порядок этапов.
Текущая рабочая точка — `docs/EMBER_NOW.md`; технические owners —
`docs/EMBER_TECHNICAL_HANDOFF.md`; игровые правила — `docs/EMBER_GAME_DESIGN.md`.

Не использовать этот файл как changelog. Перед планированием сверять текущий
checkout и открытые решения в `EMBER_NOW.md`.

## Видение

Ember — одиночная яркая приключенческая JRPG с постоянной группой спутников,
пошаговыми стихийными боями и видом сверху/три четверти.

Мир строится как граф компактных содержательных зон, а не бесшовный open world.
Окружение — тёплая handcrafted voxel-диорама; персонажи — выразительный pixel art;
ключевые сцены могут использовать рисованные портреты и фоны.

Главная фантазия: собрать близкую команду, исследовать красочный мир через
любопытство и находить неожиданные решения в окружении, отношениях и бою.

## Столпы

1. **Любопытство важнее маркеров.** Секреты, короткие возвраты,
   альтернативные маршруты и небольшие истории вознаграждают наблюдательность.
2. **Спутники — участники путешествия.** Они присутствуют в мире, сюжете,
   отношениях и совместных действиях, а не только занимают боевые слоты.
3. **Стихии — общий язык мира и боя.** Wet, холод, молния, огонь, лёд,
   пар и изменения поверхности должны давать предсказуемые последствия.
4. **Handcrafted voxel-диорама.** Сначала силуэт и крупные цветовые массы,
   затем осмысленная детализация; art voxel не равен игровому блоку.
5. **Пошаговый бой уважает время игрока.** Очередь, цели, реакции и фактический
   результат читаемы; повторяемые анимации можно ускорять.

Не строим Minecraft-песочницу, бесконечный procedural world, roguelite/gacha,
Vampire-Survivors-arena или полную grid-SRPG только ради отдельного референса.

## Принятые технические и художественные решения

- Godot 4 Forward+ — единственный runtime и authoring stack.
- Обычный ландшафт и базовый язык окружения ориентируются на 16 ячеек по каждой
  горизонтальной оси игрового блока: крупный силуэт важнее мелкого шума.
  32 voxels/block остаются доступным выбором для отдельных намеренно необычных,
  в том числе мистических,
  объектов и деталей. Плотность существующих Resource не меняется глобально.
- Мир и бой используют одну voxel-библиотеку, но разные данные размещения:
  exploration layout не хранит боевые свойства, Battlefield не владеет миром.
- Вода — отдельная поверхность над вручную созданным дном; визуальные эффекты
  воды не меняют voxel-геометрию дна.
- Основной композиционный ракурс — ортографический; свободный preview допустим,
  но результат проверяется в игровом ракурсе.
- Новая система вводится только после проверки существующего owner и доказательства,
  что существующая архитектурная граница не закрывает задачу.

### Общая фактура материалов для трёх миров

Художественный ориентир уточнён автором17 октября: акварельная живописность,
чтобы каждый игровой кадр воспринимался как нарисованная картина. Genshin —
ориентир цельности цвета/света и спокойной фактуры. Крупные ясные мазки и
неброские материалы читаются с изометричной камеры; аккуратные углубления
поддерживают явные борозды и форму. Принятая спокойная кора дуба задаёт направление
дальнейшей работы; это рабочая основа для улучшений, не финальная приёмка всего мира.

Подтверждено автором16 октября: **воксельная геометрия — источник правды**.
Генераторы/кисти изменяют одну основу; обычный детальный, гранёный и воксельный
облики — её производные. Обычный облик сохраняет острые грани, сглаживание локально
и управляемо. Гранёный упрощает исходную форму, а не восстанавливает её из сглаженной.
Уточнение формы камня: крупные неровные плоскости разной формы (в том числе
четырёх- и пятиугольные) и отдельные сколы. Внутренние треугольники одной
плоскости не должны читаться по свету. Больше треугольников само по себе не
означает больше полезной детали. Силуэт и наклоны берутся из общей voxel-основы;
локальная детализация обычного вида не меняет остальные облики.

Крупный излом, меняющий форму камня, сначала создаётся в общей воксельной основе
и затем сохраняется во всех обликах. Ступеньки одного наклона не считать автоматически
отдельными сколами; не компенсировать отсутствие формы в Source выемками внутри mesh.
16 октября автор разрешил такую правку двух LAB-камней и пересборку трёх видов.
После сравнения материалов автор принял форму как достаточную рабочую базу.
Фактура камня продолжается с Sol; полное соответствие B и production-перенос не закрыты.

Материал имеет свою общую подробную основу: цвет, высоту/углубления, маски,
масштаб и привязку. Обычный вид использует подробности; гранёный для выбранного
стиля оставляет спокойные крупные пятна; voxel получает квадратную дискретизацию.
Это производные одного материала, не три независимые картинки. Детали, потерянные
при пикселизации, нельзя точно восстановить обратным преобразованием: исходник
сохраняется, ручные поправки вариантов должны быть отдельными производными.
Воксельная геометрия остаётся источником формы; подробный материал её не заменяет.

Размер геометрических вокселей и пикселей материала независимы. Листва/плоскости
имеют свои правила при общих расположении/цвете/принадлежности. Материалы, покраска,
глубина, свет и согласованная физическая поверхность общие; грунтовая покраска
не попадает на отдельный камень автоматически. Ручные поправки видов производны.
Порядок приёмки: три узнаваемых геометрических облика без текстур → согласованные
материалы и свет внутри каждого облика → аномальные переходы. Для камня первый
этап достаточен для продолжения; теперь доводим материалы с Sol. Ручные поправки
производных допустимы на этапе их настройки. Общий конвертер ещё не готов.
Подробная договорённость — «Подтверждённая основа геометрии» в
`C:/Users/novos/Documents/Codex/2026-10-12/new-chat-2/outputs/EMBER_UNIFIED_VOXEL_LOOKS_PLAN_2026-10-13.md`.

Уточнение автора16 октября2026: основной игровой мир — гладкий. Воксельный и
гранёный облики прежде всего появляются локально из-за аномалий, меняющих объект
целиком или частями. Это облики одного мира, не три обязательных постоянных режима.
Свободное переключение всего вида мира, возможно как особенность персонажа, —
идея на будущее, без принятой механики. Ограниченная область аномалии уменьшает
обычную нагрузку, но не отменяет бюджет одновременно изменённых объектов.

Терминология, уточнение автора 20 октября 2026: «гладкий/подробный» облик — это НЕ
сглаживание формы. Цепочка: воксели (Source) → low poly (крупные плоские грани) →
подробный мультяшно-реалистичный облик: те же крупные плоскости и силуэт, плюс добавленные
детали (мелкие грани/сколы и щели геометрией, глубина/POM, рисунок текстуры, вырезанный
рельеф). Скругление всего («обкатанный камень») не цель; скругление допустимо только как
локальное правило. Ориентир — картинка камня с гранями разного наклона, трещинами и спиралью.

Решение автора 22 октября 2026 (цель материалов): материал — не один набор ползунков, а
«материал из слоёв» в существующем окне Pattern (без узлового редактора и второго renderer):
рисунок, рёбра граней (фаска на выпуклых, зазор/шов на вогнутых и стыках частей), своя
плоскость на каждую грань (оттенок, поворот/сдвиг рисунка, градиент), трещины/сколы от рёбер
по номеру грани, глубина, рамка света; слои включаются/выключаются и переиспользуются между
материалами (камень, песок, кора). Порядок: сначала одноразовая проба слоёв на одном камне
(в копии проекта: А — рёбра, Б — рёбра + плоскость на грань, В — Б + трещины/сколы), по её
итогам согласуется отдельный срез «материал из слоёв» (существующие группы style_rim_*/depth_*/
form_pull_mm становятся слоями, данные cartoon_stone переносятся без потерь). Схему слоёв заранее
не проектировать: набор слоёв определяет проба. Свет/блик, пропадающий на части полигонов,
разбирается после текстур. Перед расширением системы на другие объекты — ревизия направления
(что лишнее/старое, не упрёмся ли в стену на составных объектах вроде моста).

Дальнейшая договорённость16 октября: после художественной проверки трёх обликов
на дереве, камне и дороге сделать единый переключатель для разработчика — весь
мир или отдельный объект окружения. Земля входит в этот маршрут; использовать
существующие Source/terrain look paths, не начинать второй terrain renderer.
Персонажи пока исключены: их форму автор планирует дорабатывать вручную.
Общий выбор облика/материалы/пространственная граница и физика должны быть едины;
способ получения формы может учитывать тип поверхности (ветви/листва, твёрдый
предмет, земля). Универсальная автоматизация условна: сначала принять эти три
репрезентативные пробы, затем переносить в основной runtime/editor и проверять
сохранение/Undo/обновление производных. Имеющийся terrain morph не считать готовым
произвольным 3D превращением всех объектов.

Решение автора 2026-10-14: сначала создавать красивую мультяшную фактуру для
гладкого мира. Принятые брусчатка/камень/песок — ориентир качества и читаемости.
Цвет, рисунок, ручная покраска и декоративный рельеф составляют общую основу
материала; остальные подачи выводятся из неё, не рисуются как несвязанные наборы.

- Первый мир: гладкая живописная подача с ясными мазками и сдержанным рельефом.
- Второй мир: гранёная low-poly форма и минимальная спокойная фактура из того же
  подробного материала. Сохраняем палитру и крупный рисунок, ослабляем мелкую
  цветовую детализацию; обязательный pixel filter сюда не переносим.
  Гранёные дуб и камень реализованы в LAB, общий стиль ещё требует приёмки;
  обобщение low poly на землю/другие объекты ещё не выполнено.
- Третий, воксельный мир: пикселизация обязательна. Цветовые клетки и характер
  рельефа согласуются с исходной воксельной сеткой объекта; материал должен
  восприниматься естественной частью квадратной формы. Крупный рисунок и размер
  трещин/пятен сохраняются, мелкие детали осмысленно упрощаются.

Общее правило не означает одинаковую фильтрацию цвета, нормалей и POM во всех
мирах. Pixel-вид не сводится к nearest поверх мыльного изображения или к
округлению POM-смещённых координат. Непрерывный материал и его дискретная подача
должны пользоваться устойчивой общей привязкой к исходнику/поверхности.

Плавный переход подачи материала — желаемое направление, технически возможное
через согласованное смешивание производных видов одного рисунка. Способ и вид
перехода ещё требуют отдельной пробы. Переход геометрии/силуэта — самостоятельный
срез с проверкой физической поверхности; он этим решением не реализован.
Приёмка каждого материала обязательна последовательно в трёх видах: обычный
подробный → гранёный с минимальной фактурой → воксельный с квадратным рисунком.
Затем сравнить три вида рядом: объект остаётся узнаваемым, материал — родственными
подачами одной основы. Проверять крупно и с игровой камеры, в движении, днём,
вечером и ночью, при боковом и контровом свете. Оценивать также общую сцену:
камень, земля, дорога, трава и дерево должны сочетаться внутри каждого вида.
Сохранять POM/глубину, общий свет и кромку, настройки листвы и ручную покраску.

После этой художественной приёмки — отдельная проба движущейся сферы аномалии:
внутри её области плавно меняются геометрия и материал частей земли/объектов,
а снаружи сохраняется обычный мир. Проверить вход, выход и возврат исходного вида.
Общая пространственная граница принадлежит существующей системе world look/аномалий;
не вводить второй renderer или независимую физику для каждого вида. Способ плавной
перестройки и согласование с одной физической поверхностью ещё предстоит проверить.

## Этапы продукта

### D0 — ключевые решения до production-контента · принято

Зафиксирован механический baseline и направление стартовой главы:
- авторский протагонист;
- постоянная активная группа до четырёх героев;
- authored-встречи вместо процедурного гринда;
- каноническая стартовая глава на портовом острове;
- расследование аномалии и древний комплекс под маяком;
- отношения между персонажами являются частью путешествия, но не требуют
  заранее универсальной числовой системы.

Имена и финальный визуальный дизайн остаются контентными решениями,
а не частью schema.

### D1 — правила боя · лабораторный baseline реализован

Единый resolver уже покрывает основной лабораторный baseline:
- preview/commit;
- очередь и staged command selection;
- движение, вертикальность и pathfinding;
- стихии и состояния;
- предметы, умения и парные техники;
- positional auto-approach;
- victory/defeat, XP и Retry;
- предбоевая расстановка.

Числовой баланс остаётся настраиваемым; полный игровой маршрут и отдельные
ручные gates ещё открыты. Новые механики добавляются только если их нельзя
выразить существующими Action/Effect/Status контрактами.

### D2 — вертикальный gameplay loop · graybox существует

Отдельно уже существуют exploration, interactions/action chains, dialogue/VN,
shop, inventory/equipment, HP/defeat, quests, активная группа 1–4,
переход в бой и возврат результата. Для группы остаётся ручная приёмка
в Forward+.

Доказательный шаг D2 — небольшой сквозной участок канонического graybox,
собранный на существующих owners без второго world/party/save state.

### D3 — грамматика production-зоны · следующая крупная цель

Стартовая глава должна связать:
- портовый причал и первую аномалию;
- компактную часть города и особняк;
- несколько направлений расследования и улики;
- дневник деда;
- ночное проникновение;
- древний комплекс под маяком;
- подготовительный бой и бой со стражем;
- развязку через восстановление равновесия узлов.

Сначала проектируются сцены, NPC, улики, комнаты, encounters и нужные assets.
Только затем graybox собирается существующим authoring loop.

### D4 — отношения · после первого сквозного участка

Сначала проверить минимальный вертикальный срез:
один спутник → одно изменение отношений → одна добровольная сцена →
одно видимое последствие в путешествии или совместном действии.

Не вводить заранее универсальную шкалу для всех персонажей.

### D5 — art lock · после production-zone

Только после рабочей production-зоны фиксируются:
- камера;
- масштаб;
- палитровая дисциплина;
- освещение;
- вода;
- плотность деталей;
- язык персонажей и окружения.

До этого assets являются проверочными, а не финальным объёмом производства.

## Инструментальный проход перед production-контентом

Перед наполнением главы была принята «Воксельная мастерская окружения»:
Причал используется как площадка проверки инструментов, а не как отдельная игра.

Принцип:
- размещение, сборка и редактирование мира происходят в 3D-сцене;
- выбранная voxel-деталь может редактироваться также в существующем Canvas;
- source — `EmberVoxelModelResource`;
- mesh/collision/prefab/thumbnail — производные данные;
- arbitrary Mesh/GLB → voxels не является обязательной частью пайплайна;
- старые карты, модели, сохранения и пользовательские изменения сохраняются.

На `main` уже есть Object Canvas, формы, точная расстановка, сборки и секции,
object brush, генераторы объектов, рельеф, берег/дно и вода. Отдельный
`scenes/world_canvas.tscn` даёт проверочную большую карту, а режим
«Редактировать мир» переносит существующие операции в 3D без второго editor
или формата мира. Автоматические проверки прошли; ручная проверка удобства,
визуала, сохранения и игрового движения остаётся открытой.

Для следующих обычных локаций направление — компактная земля с 16 ячейками на
блок. Пресеты ровной земли и берега уже подготовлены; их вид и работу большой
кисти нужно принять в обычном 3D-редакторе. Адресуемые участки/частичный край
и генератор одной области до 96 м реализованы; первый сохраняемый прямоугольный
план с параметрами также реализован, работа подтверждена автором. Локальное плато
поверх сухой земли готово к авторской пробе. Дальнейшее развитие:
остров, берег, возвышенность, площадка и позже дорога.
Размер области, горизонтальный масштаб форм, высота, покрытия, плотность
объектов и независимые seed настраиваются отдельно. После применения земля
и объекты остаются у существующих владельцев; разметка не становится вторым
runtime-миром. Детальный порядок и owners — в
`EMBER_WORLD_AUTHORING_ARCHITECTURE.md` и `EMBER_EDITOR_UI_REWORK_PLAN.md`.

Массовый world authoring — World Layout, планировщики земли и объектов,
3D world brushes для больших участков, дороги, биомы и building massing —
описан в `EMBER_WORLD_AUTHORING_ARCHITECTURE.md`. Это направление после
текущего editor-среза; пока реализованы только простые пресеты новой карты.

Подробные реализации и уже закрытые итерации не являются частью продуктового
плана. Их история живёт в Git и тематических editor-документах.

## Игровые системы редактора

По выбору автора 2026-10-11 отдельный текущий проход — общие модули создания
предметов, экипировки и боевого контента. Доступ без выбранной карты; единое
рабочее пространство с библиотекой, редактором, связями и проверкой результата.
Существующие Resources/catalogs, ExploreState/PartyState и единственный combat
preview/commit остаются owners. Граф нужен для ветвлений; простая цепочка
эффектов редактируется списком. Новый готовый runtime framework не внедряется.

   обновляет изменённую запись; прежние cache/UID/Resources сохраняются. Rapid/
   sequential native lifecycle + FileSystem/cache/UID, полный editor и full cycle
   PASS. Точный C++ frame без symbols/dump не установлен; это проверка данного
   trigger, не всех native/GPU сценариев. Authored Save/Undo/Redo/reopen,
   live input/narrow/125% и свои saves OPEN. Owners/evidence — Technical Handoff.

## Рабочая последовательность

Уточнение автора 2026-10-10: старые игровые города/карты выводятся через архив;
новый Ember развивается на актуальной native основе, без обязательной подгонки
под старый контент. Старт F5 — landscape_compact; действующие общие mechanics
owners сохраняются. Архив/границы и последовательность выхода — JOI Exit Plan.
Это решение о старой реализации/контенте, не переписывание канонической главы.

Цель инструментального прохода — автор самостоятельно строит локацию, наполняет
событиями и проверяет её в игре. Причал может быть проверочным местом, но точный
первый законченный эпизод ещё нужно выбрать из канонической главы.
Пункты — последовательность результатов, не один контракт и не сроковой план.

1. **Основа большой карты.** По запросу автора от 2026-10-03 исследовать и
   последовательно развивать генератор/разметку для островов 256–512 м, затем
   увеличивать масштаб по замерам. Адресные участки и рельеф одной области реализованы;
   сохраняемый прямоугольный план реализован; уровни моря/озёр, реки/водопады
   предшествуют расширению биомов. Owners, ограничения и порядок —
   в World Authoring Architecture; авторская проба основы остаётся открытой.
   При подготовке сборок обязательно вернуться к «Сборки: фундамент, момент
   внедрения и бюджет диска» в том же документе: выбранные карты/данные, чистый
   старт и размер пакета; streaming/HLOD внедрять по памяти/кадру до дальнейшего
   существенного роста мира, отдельными контрактами.
2. **Живая опора карты и отложенная вода/материалы.** Закрыть затронутые gates:
   создать землю, вручную исправить, назначить материалы, поставить объекты,
   пройти и сохранить. Художественная приёмка последней пробы материалов
   отложена автором; вода/материалы сохраняют точный stop-line своих срезов,
   новые эффекты и общий перенос автоматически не добавляются.
3. **Минимальный планер.** Последовательно задать области, гору и площадку,
   с контролем игровых ровных мест и пологих переходов; затем водные связи,
   дороги до/после генерации и planner наполнения. Детали и порядок влияния —
   World Authoring Architecture → «Параметры без путаницы масштаба». Preview→Apply, ручная правка и
   повторное открытие одной проверочной локации; не автоматический город целиком.
4. **Наполнение.** Разместить нужные объекты и персонажей, точки появления,
   согласовать минимальные маршруты. Домики — поздний generator по потребности,
   а не предварительное требование. Сохранить party/save baseline и принять группу.
   Вариант существующих генераторов с полублоками и возможной диагональю отложен
   отдельно: World Authoring Architecture → «Отложенная вариация формы объектов».
5. **События и переходы.** Редактируемые квесты/действия/сценки, магазины,
   диалоги и триггеры на прежних owners. Выбранный объект показывает связи;
   нужный preview доступен из 3D. Проверить условия, последствия и загрузку.
6. **Боевая встреча.** Создать нужную 3D-арену и участников, связать запуск,
   результат, награды и возврат. Compact-декор не меняет Battlefield/hitbox owner.
   Принять существующие бой, поражение/Retry и party/save сценарии.
7. **Сквозной эпизод.** Пройти выбранный маршрут от начала до последствия,
   проверить загрузку и отсутствие тупиков. Затем развивать полную главу,
   отношения и art lock по D3–D5, сохраняя спецификацию GDD.

Editor UI улучшать на соответствующем шаге. Игровой UI имеет отдельную визуальную
приёмку; финальный стиль не фиксируется до доказанного игрового пути.
Переносимые мировые инструменты используют общий panel host; новые панели
подключать к нему. Результат, границы и UI gates — Terrain Authoring → «Рабочий интерфейс».
Переключения и отложенные идеи — по Workflow; текущая точка — только NOW.

После каждого самостоятельного среза:
- targeted automatic gates;
- ручная проверка затронутого ощущения/визуала в Forward+;
- фиксация принятого состояния;
- следующий срез не должен скрывать долг предыдущего.

## Границы канонического graybox

Первый graybox включает только необходимую часть портового города,
нужные интерьеры и первый данж — не весь стартовый остров.

В него не входят:
- crafting;
- случайные аффиксы;
- бесконечный procedural content;
- полная озвучка;
- массовая миграция неиспользуемого legacy-контента;
- сложные stacked battle floors без доказанной необходимости;
- отдельная новая party/save система.

Stale prefab и legacy-assets переносятся только если реально нужны production-зоне
и прошли визуальный/функциональный parity.

## Как использовать этот документ

`EMBER_PRODUCT_PLAN.md` отвечает только на вопросы:
- что за игра строится;
- какие продуктовые этапы существуют;
- в каком порядке их доказываем;
- что сознательно не входит в текущий масштаб.

Он не хранит:
- историю ежедневных правок;
- benchmark-цифры;
- подробные test logs;
- несколько итераций одного editor-инструмента;
- текущий Git status;
- точный список открытых manual gates.

Для этого использовать соответственно `EMBER_NOW.md`,
`EMBER_TECHNICAL_HANDOFF.md`, `MIGRATION_TEST_PLAN.md` и Git history.
