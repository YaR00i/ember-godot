# Ember — карта документации

Обновлено: 2026-09-16.

Этот файл — входная точка в документацию Ember. Он нужен, чтобы человеку или AI-агенту не приходилось читать все большие документы подряд и чтобы одна и та же мысль не размножалась в нескольких местах.

## С чего начинать

Для обычной задачи достаточно такого маршрута:

1. `../AGENTS.md` — обязательные правила работы с репозиторием.
2. `EMBER_NOW.md` — текущая точка, открытые ручные проверки и ближайший следующий шаг.
3. Этот файл — выбрать только релевантный канонический документ.
4. `EMBER_WORKFLOW.md` — Task Contract, проверки, приёмка и handoff.

Большие файлы открываются поиском по нужному разделу. Читать `EMBER_PRODUCT_PLAN.md`, `EMBER_GAME_DESIGN.md`, `EMBER_TECHNICAL_HANDOFF.md` или `MIGRATION_TEST_PLAN.md` целиком по умолчанию не нужно.

## Канонические документы

### Текущая работа

- `EMBER_NOW.md` — только текущий milestone, незакрытые gates, ближайшие шаги и решения, которые действительно нужны сейчас.
- `EMBER_WORKFLOW.md` — постоянный процесс разработки: исследование, Task Contract, реализация, проверки, приёмка, Git checkpoint и передача между thread.
- `../MIGRATION_TEST_PLAN.md` — подробные regression/manual gates. Это не продуктовый roadmap.

### Продукт и игра

- `EMBER_PRODUCT_PLAN.md` — долговечное направление продукта, порядок крупных этапов и принятые продуктовые границы.
- `EMBER_GAME_DESIGN.md` — правила игры, содержание вертикального среза, бой, исследование, партия, сюжетные и игровые решения.
- `EMBER_WORLD_AUTHORING_ARCHITECTURE.md` — канонический план будущего authoring-слоя мира: 3D world brushes, World Layout, planners, биомы, массовая расстановка и building massing.

### Техническая истина

- `EMBER_TECHNICAL_HANDOFF.md` — актуальные owners, технические контракты, ограничения и доказанные риски. Предпочтительна текущая истина, а не хронология всех экспериментов.
- `EMBER_ADDONS.md` — границы и устройство editor/addon-части.
- `EMBER_SURFACE_LARGE_PROFILE.md` — профиль больших Surface и связанные ограничения.

### Редакторы и UX

- `EMBER_BRUSH_WORKSHOP_PLAN.md` — Surface Canvas, кисти, выделение, штампы и генеративные источники внутри мастерской.
- `EMBER_EDITOR_UI_REWORK_PLAN.md` — принятая переработка интерфейса мастерской.
- `EMBER_EDITOR_UX_AUDIT.md` — UX-аудит и найденные проблемы редактора.
- `EMBER_OBJECT_INSPECTOR_DESIGN.md` — Object Inspector и scene-owned authoring.
- `EMBER_UI_PIPELINE.md` — общий маршрут editor/player-facing UI.
- `EMBER_VISUAL_LIBRARY_DESIGN.md` — визуальная библиотека и связанные authoring-потоки.

### Миграция и специальные переходы

- `EMBER_JOI_EXIT_PLAN.md` — условия полного выхода из legacy JOI.
- `../LIGHTING_GATE.md` — отдельный gate освещения.

## Что хранить где

`EMBER_NOW.md` отвечает на вопрос: **«где мы прямо сейчас и что проверяем следующим?»**

`EMBER_PRODUCT_PLAN.md` отвечает: **«куда идёт продукт и в каком порядке?»**

`EMBER_GAME_DESIGN.md` отвечает: **«как устроена сама игра?»**

`EMBER_TECHNICAL_HANDOFF.md` отвечает: **«как это сейчас технически устроено и кому принадлежат данные?»**

Специализированный plan отвечает только за свой домен. Например, правила будущей генерации леса, World Layout и building massing живут в `EMBER_WORLD_AUTHORING_ARCHITECTURE.md`, а не копируются подробно в NOW, Brush Plan и Product Plan одновременно.

## Гигиена документации

Документы не должны превращаться в журнал каждого разговора с Codex.

- После завершённого среза переписывать текущий статус, а не бесконечно дописывать новую запись сверху.
- Старый superseded-текст не обязан оставаться в текущем документе только ради истории: история уже есть в Git.
- Численные benchmark/evidence сохранять там, где они действительно нужны для технической границы; в NOW достаточно вывода и открытого риска.
- Не дублировать один и тот же контракт в нескольких файлах. Другие документы дают короткую ссылку на owner-документ.
- Новый документ создаётся, только если появился самостоятельный долговечный домен. Для маленькой feature отдельный отчёт не нужен.
- При обновлении большого старого файла удалять или сжимать устаревшую хронологию только после проверки, что действующая истина перенесена в каноническое место.

## Текущий долг документации

К 16 сентября `EMBER_NOW.md`, `EMBER_PRODUCT_PLAN.md`, `EMBER_TECHNICAL_HANDOFF.md` и `MIGRATION_TEST_PLAN.md` накопили много полезной, но местами хронологической информации. Этот checkpoint **не переписывает их массово и не выбрасывает сведения**.

Дальнейшая чистка выполняется постепенно при работе с соответствующим доменом:

1. выделить действующую истину;
2. перенести её в канонический раздел;
3. оставить в NOW только текущую точку;
4. убрать дубли и superseded-описания;
5. использовать Git как архив прежних формулировок.

Так мы уменьшаем контекст для новых thread без риска потерять важные решения.
