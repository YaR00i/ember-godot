# Ember — пайплайн UI

Статус: обязательный процесс для значимых изменений editor UI и игрового UI.

Этот документ дополняет `EMBER_WORKFLOW.md`. История и текущие контракты
интерфейса редактора остаются в `EMBER_EDITOR_UX_AUDIT.md`.

## Основное решение

Нативный Godot — основной способ прототипирования и реализации UI.

- Editor UI, Inspector, dock, main-screen workspace, Graph и Surface Canvas
  проектируются сразу в настоящем Godot. Их нельзя точно оценить вне editor
  theme, Container layout и EditorPlugin lifecycle.
- Небольшой игровой UI — одна панель, модальное окно или понятное изменение —
  также сразу собирается в Godot и показывается пользователю.
- Для крупного player-facing интерфейса сначала проводится отдельное визуальное
  согласование. Формат выбирается по задаче: референс, набросок, изображение,
  интерактивный прототип или HTML/CSS/JS.
- HTML не является обязательным этапом. Он используется, когда помогает дешевле
  проверить несколько экранов, композицию, состояния или адаптивность до
  переноса в Godot.

## Как определить размер UI-задачи

### Малая

Пример: изменить одну карточку, диалог, кнопку, статус или расположение нескольких
существующих элементов.

Маршрут: изучение существующего UI → нативное изменение → targeted test →
скриншот/ручная проверка в Godot → комментарий пользователя.

### Значимая editor UI

Пример: новый dock, workspace, Inspector flow, toolbar hierarchy или сложный
authoring dialog.

Маршрут: UI-brief → схема состояний и ownership → нативный Godot prototype →
проверка в реальном редакторе → согласование пользователя.

### Крупная player-facing UI

Пример: постоянный HUD, бой, инвентарь, меню группы или несколько связанных
экранов.

Маршрут: UI-brief → визуальный target → Approval A → нативная реализация →
функциональная и визуальная проверка → Approval B.

## Этап 1. Изучить существующую поверхность

До вопросов и макета агент находит:

- сцену `Control`/`CanvasLayer`, скрипты и текущие Theme Resources;
- источник gameplay/editor данных и команду, которая их меняет;
- существующие экраны, состояния, сигналы, shortcuts и input routing;
- целевые разрешения и текущую design size;
- targeted tests, screenshots и ручные gates;
- связанные решения в product plan, handoff и UX audit.

Нельзя создавать второй UI-owner одной и той же настройки, отдельный state model
или новый Theme только потому, что так удобнее текущему экрану.

## Этап 2. Составить короткий UI-brief

Перед реализацией должны быть понятны:

1. кто открывает экран и зачем;
2. главное действие пользователя;
3. вход и выход из экрана;
4. обязательные normal, hover, selected, disabled, loading, empty и error
   состояния — только те, которые реально нужны;
5. мышь, клавиатура, геймпад, drag/drop и Cancel/Esc, если применимо;
6. русская copy, иконки и данные;
7. минимальный и основной viewport;
8. наблюдаемые условия приёмки.

Агент сначала объясняет контекст простыми словами и даёт рекомендацию. Вопросы
задаются небольшими порциями только о визуале, поведении и игровом ощущении,
которые нельзя вывести из существующего проекта.

## Этап 3. Выбрать способ визуального согласования

Используется самый дешёвый способ, который действительно позволяет принять
решение:

- референс — когда нужно подтвердить направление;
- быстрый wireframe — когда спорна композиция;
- изображение — когда важнее атмосфера и визуальная иерархия;
- нативный Godot prototype — когда важны editor theme, реальные данные или
  интеракция;
- HTML — когда крупный игровой интерфейс имеет несколько экранов и состояний,
  которые быстрее согласовать вне runtime.

Макет является контрактом только для явно согласованных свойств: композиции,
иерархии, размеров, copy, иконок и состояний. Непрошенные controls, подсказки,
декоративные блоки и функции не добавляются ради «полноты».

Используются настоящие разрешённые ассеты или честные временные изображения,
которые представляют объект. Текстовые буквы вместо предметных иконок допустимы
только для самого раннего wireframe, но не для визуального approval.

### Approval A — визуальный target

Требуется для крупного player-facing UI. Пользователь утверждает:

- состав экранов;
- визуальную иерархию и стиль;
- расположение основных элементов;
- важные состояния и взаимодействия;
- целевые размеры окна.

Для малой UI-задачи и editor UI отдельный Approval A можно пропустить: реальный
Godot prototype становится первым предметом обсуждения.

## Этап 4. Реализовать нативно в Godot

### Layout

- Использовать `Control` и вложенные `Container` как владельцев адаптивной
  компоновки.
- Не смешивать ручные offsets с Container-owned layout без доказанной причины.
- Anchors определяют привязку к краям; Containers — внутреннее распределение.
- Длинный контент получает ограничение размера, перенос, tooltip или
  `ScrollContainer`, а не бесконечный minimum size.
- Основные действия не должны менять положение при смене режима.

### Визуальная система

- Общие цвета, типографика, отступы, панели, кнопки и состояния принадлежат
  существующему Theme Resource или обоснованным theme type variations.
- Локальные overrides используются для исключений, а не как параллельная
  дизайн-система.
- Система создаётся только в объёме текущих экранов; варианты «на будущее» не
  добавляются.

### Данные и команды

- UI показывает состояние и маршрутизирует команды, но не становится вторым
  owner gameplay Resource или editor draft.
- Общая математика и validation остаются в чистом leaf-модуле.
- Preview использует тот же расчёт, что и commit.
- Тяжёлая операция фиксируется на pointer-up, подтверждении или Enter, а не при
  каждом движении указателя.
- Editor-only камера, selection, panel size и фильтры сохраняются только через
  editor layout/state contract, если для этого уже выбран owner.

### Input и lifecycle

- UI-события обрабатываются через сигналы и `_gui_input()` там, где это нужно.
- Проверяются `mouse_filter`, `accept_event()`, focus и scroll propagation.
- Ввод UI не должен попадать в gameplay или viewport gesture после обработки.
- Drag/drop и pointer capture всегда завершаются на release, Cancel, hide и
  смене режима.
- Focused текстовое поле сохраняет штатное редактирование; глобальные shortcuts
  не должны неожиданно забирать его клавиши.
- EditorPlugin использует штатные save/unsaved/layout callbacks; собственный
  скрытый lifecycle рядом не создаётся.

## Этап 5. Проверить UI

### Автоматически

- parse/check затронутых scripts;
- targeted test для данных, команд, layout и input contract;
- Undo/Redo, save/reopen, discard и validation для authoring UI;
- mount/unmount, hide/show и resource switch, если UI подписывается на сигналы;
- связанные Graph, Surface, content или runtime regressions.

### В настоящем Godot

Текущие базовые размеры Ember:

- `1600×900` — основная design size проекта;
- `1280×720` — компактный обязательный gate;
- дополнительные aspect ratio и DPI — когда они входят в target конкретного
  игрового экрана.

Проверяются:

- полный основной сценарий мышью;
- keyboard focus и gamepad navigation, если экран их поддерживает;
- hover, selected, disabled, error, empty и Cancel states, которые входят в
  brief;
- отсутствие обрезанного текста и недоступных кнопок;
- отсутствие новых Console errors, warnings, leaks и stale callbacks;
- input isolation от игры и 3D viewport;
- Forward+ кадр и сравнение с утверждённым target.

Скриншот доказывает только layout и визуальное состояние. Drag/drop, фокус,
клики, закрытие, сохранение и игровое ощущение проверяются интерактивно.

### Approval B — готовый Godot UI

Пользователь видит интерфейс непосредственно в Godot и оценивает:

- соответствует ли он согласованному визуальному target;
- понятна ли иерархия действий;
- удобно ли читать и управлять экраном;
- подходит ли темп, анимация и обратная связь игре.

Отличия от макета показываются заранее и объясняются. Техническое ограничение не
маскируется как дизайнерское решение.

## Definition of Done для UI

UI-срез готов, когда:

- все согласованные функции и состояния работают;
- layout проверен в заявленных размерах;
- input не протекает в gameplay;
- один и тот же owner используется UI, preview и commit;
- обязательные editor lifecycle проверки пройдены;
- нет новых Console errors;
- visual/runtime gate пройден или честно помечен `degraded`;
- пользователь выполнил нужное визуальное согласование;
- долговечное решение отражено в существующем UX audit или handoff.

## Что не делать

- Не переносить Unity UXML/USS или Unity CLI правила в Godot по названию.
- Не делать HTML обязательным для каждого экрана.
- Не считать HTML implementation source of truth после переноса в Godot.
- Не добавлять второй UI state owner, renderer или универсальный UI framework.
- Не строить UI заново в `_process()` и не опрашивать состояние каждый кадр без
  доказанной необходимости.
- Не создавать отдельные flow/state/QA документы для простой панели, если brief
  и существующие tests уже сохраняют решение.
- Не объявлять визуал принятым без просмотра пользователем.
